## 1. 요약

**다시 만들기로 한 결정은 옳다.** 문제는 코드 품질이 아니라 두 가지 구조에 있다.

1. **데이터 기반의 천장** — 네이버 모바일 API로는 전 종목 목록·유통주식수·기관 보유·업종
   분류를 얻을 수 없다. 그래서 CANSLIM 7개 중 3개(S·I·L)가 대체 지표로 채워졌고,
   CANSLIM의 심장인 **전 종목 상대강도 백분위(RS Rating)는 원리적으로 불가능**하다.
2. **제품 형태** — 종목 하나를 입력받아 채점하는 현재 구조는 "2,700개 중 무엇을 볼
   것인가"를 좁히는 CANSLIM의 목적과 반대 방향이다. 이미 정한 종목을 확인해 주는
   확증 편향 증폭기로 기능한다.

그 위에, 판정 기준이 오닐 원전에서 **일관되게 느슨한 방향으로** 이탈해 있어
"5/7 통과"라는 숫자가 실제로 무엇을 의미하는지 말할 수 없는 상태다.
반면 Metric/Status/Source 모델, "판단불가 ≠ 불합격" 원칙 등 계승할 자산도 분명하다.

## 3. 데이터 계층 평가

네트워크는 `naver.py` 한 파일에 격리되어 있고(잘된 설계), 6개 비공식 엔드포인트에서

| 유통주식수(float) | **S** | ✗ | 거래량 배수로 대체 |
| 기관 보유자 수·보유 비중 | **I** | ✗ | 외국인 소진율 추세로 대체 |
| 업종/섹터 분류 | L (주도 업종) | ✗ | 아예 없음 |

대체 지표로 메운 항목이 7개 중 3개다. 이건 데이터 소스를 바꾸지 않는 한 반복된다.

### 3-2. 조용한 퇴화가 기본값 — 관측 불가능한 실패

스키마가 바뀌면 크래시가 아니라 **'판단불가'로 조용히 퇴화**한다. 사용자는 도구가
고장난 것을 모른 채 잘못된 점수를 본다. 대표 경로:

- **한글 라벨 정확 일치 의존.** 일봉 헤더(`prices.py:19-27`)와 재무 행 라벨
  (`valuation.py:22-24`의 `"매출액"`, `"EPS"`, `"ROE"`)을 문자열 완전 일치로 찾는다.
  실패 시 예외 없이 `None` → UNKNOWN. 특히 **은행·보험·증권은 "매출액"이 아니라
  "영업수익"** 표기라 금융 섹터 전체에서 PSR·매출 성장이 조용히 비는 것으로 추정된다.
- **JS 리터럴 파싱의 전역 치환.** `text.replace("null", "None")`(`prices.py:43`) 후
  `ast.literal_eval`. 응답 어디든 문자 "null"이 오면 깨지고, 열이 추가되면
  행 길이 필터(`prices.py:57`)가 모든 행을 버려 빈 DataFrame이 된다.
- **인코딩 함정.** `resp.encoding = resp.encoding or "utf-8"`(`naver.py:105`) —
  requests는 charset 없는 `text/*`에 ISO-8859-1을 채우므로 이 방어선은 죽은 코드다.
  한글 헤더가 깨지면 위의 라벨 매칭이 통째로 실패한다.
- **점수를 올리는 방향의 실패.** UNKNOWN은 분모에서 빠지므로(`models.py:86-99`)
  데이터를 못 받을수록 "3/3 통과"처럼 **점수가 좋아 보인다**. `newness.load()`가
  모든 예외를 삼키는 것(`newness.py:219-223`)과 결합하면, 네트워크 실패가
  통과율을 인위적으로 올린다.

그 외: 429의 `Retry-After` 무시, 403 즉시 포기(봇 차단의 최빈 코드), 요청 세션
미사용, 캐시 파일 무한 증식(만료 삭제 없음, sise URL에 날짜가 들어가 매일 새 파일),
서버 로컬 타임존 사용(UTC 서버에서 KST 새벽에 하루 어긋남).

|---|---|---|---|
| **C** | 분기 EPS +25%↑ **그리고 분기 매출 +25%↑**, 2~3분기 성장 **가속**, 일회성 이익 제외 | EPS YoY 단일 조건 (`canslim.py:81-94`). 매출 데이터는 파싱돼 있는데 안 씀. 가속 여부는 문구로만 표시 | 🔴 매출·가속 미구현. 전년동기 EPS 1원이면 +99,900%로 통과 — 저기저(low base) 방어 없음 |
| **A** | **3년 연속** 연간 EPS 증가, 연 25%↑, ROE 17%↑ | 첫해·끝해 **2점 CAGR** (`valuation.py:87`) + 분기 ROE 최신값 | 🔴 중간 해 급감해도 통과 (단조증가 미검증). ROE가 연율화 값인지 분기 실적치인지 미확인 — 후자면 임계값이 4배 어긋남 |
| **N** | 새 재료 + 베이스 완성 후 **피벗 돌파, 피벗 +5% 이내에서만 매수**. 그 위는 매수 금지 | 52주 최고가의 **85% 이상**이면 통과 (`canslim.py:31`) + 키워드 재료 AND | 🔴 **방향이 반대** — 오닐이 "베이스 안이거나 조정 중"이라 사지 말라는 고점 -15% 구간을 합격 처리. 베이스·피벗 개념 자체가 없음. 재료 AND는 원전에 없는 추가 제약인데 오탐(§2-5)으로 오염 |

| **I** | 기관 **보유자 수**의 분기 증가, 우수 펀드, **과잉보유 회피** | 외국인 소진율 60거래일 변화 > 0 (`canslim.py:240-265`) | 🔴 국내 기관(연기금·투신) 미반영 — `organ_net` 데이터가 있는데 판정에 안 씀. +0.01%p도 합격(엡실론). 과잉보유 상한 없음 |

점수에서는 1/7로 취급). `passed/judged` + UNKNOWN 분모 제외는 §3-2에서 본
"실패할수록 점수가 오르는" 역설을 만든다.

**N의 재료 탐지 추가 문제** (`newness.py`):
- NOISE에 `"결산실적공시"`, `"매출액또는손익구조"`가 있어(`newness.py:26`)

## 5. 밸류에이션 로직 평가

- **TTM 연속성 미검증** (`valuation.py:253`): EPS가 있는 분기만 모아 마지막 4개를
  합산한다. 중간 분기가 결측이면 **비연속 4분기(15개월치)**를 "4개 분기 합산"이라며
  PER을 계산한다.
- **Q+2 역산의 오차 증폭** (`valuation.py:127-173`): 확정 분기가 많이 쌓일수록
  잔차가 작아져, 연간 컨센서스의 5% 오차가 마지막 분기 추정에서 **50% 오차**로
  증폭될 수 있다. 분기 컨센서스와 연간 컨센서스는 같은 애널리스트 집합도 아니어서
  뺄셈이 그 불일치를 전부 잔차에 몰아넣는다. 🟠 라벨은 있지만 오차 크기가 상황에
  따라 몇 배씩 달라진다는 사실은 표시되지 않는다. (음수 미방어는 §2-3)
- **PEG 분모가 열마다 다름**: 현재 열은 과거 2년 CAGR(`valuation.py:273`),
  나머지 열은 연간 컨센서스 성장률(`valuation.py:302,337,370`). 같은 행인데 열 간
  비교가 성립하지 않는다. 더 심각하게는 순환주 저점 회복 구간에서 forward 성장률이
  +611% 같은 값이 되어 PEG 0.009 → "극단적 저평가"로 읽히는 조작이 발생한다
  (실측 픽스처 기준). 성장률 캡이나 순환주 경고가 없다.
- **예상 ROE 체계적 과대평가** (`valuation.py:228-231`): 미래 EPS ÷ **현재** BPS.
  이익 유보로 커질 분모를 무시하므로 고성장 종목일수록 위로 편향된다.
  "근사값" 표기는 있지만 편향 방향은 없다.
- **교차검증 임계가 절대값** (`valuation.py:387`): PER 3배와 300배에 같은 ±0.15를
  적용한다. 상대오차여야 한다.

## 6. 제품 형태의 근본 문제

### 단일 종목 조회로는 CANSLIM이 성립하지 않는다

RS Rating, EPS Rating, 산업그룹 순위, 축적/분산 등급 — CANSLIM 지표의 절반은
**전 종목 크로스섹션 랭킹**이다. 종목 하나의 데이터로는 정의상 계산이 불가능하다.
L을 "지수 대비"로 대체한 것은 데이터 게으름이 아니라 **온디맨드 단일 종목
아키텍처의 필연적 귀결**이다. 현재 구조로 전 종목을 훑으면
0.34초 간격 × 종목당 4~5요청 × 2,700종목 ≈ **1시간 이상** 걸린다.

그리고 사용 순서가 방법론과 반대다: CANSLIM은 "전 종목 → 후보 축소"인데,
이 도구는 "사용자가 이미 정한 종목 → 확인". 확증 편향을 줄이는 게 아니라 증폭한다.

### 매매 규칙이 전무하다

오닐 체계의 절반은 종목 선정이 아니라 실행이다: 피벗 매수가, **-7~8% 손절**,
+20~25% 익절/8주 룰, 피라미딩, 분산일 기반 시장 이탈. 전부 없다.
"5/7 통과"만 보고 사면 오닐 체계에서 손실을 만드는 모든 경로가 열려 있다.

### 임계값이 하나도 검증되지 않았다

25%·17%는 오닐이 미국 시장 수십 년 데이터로 도출한 값이고, 0.85·1.4·60일·0.6·180일은
출처 불명의 임의값이다(`canslim.py:28-36`, `newness.py:63`). 한국 시장 유효성을
확인할 백테스트 하네스가 없어 튜닝도 불가능하다.

### 한국 시장 특수성 미반영

분기보고서 45일 공시 지연(C가 최대 4.5개월 묵은 데이터인데 기준 분기 미표시),
연결/별도 혼용, 액면분할 시 EPS 소급수정 여부 미확인, ±30% 가격제한폭,
우선주·스팩·리츠·ETF가 검색에서 안 걸러짐(`tickers.py:26`), 관리종목·거래정지 필터 없음.

## 7. 유지할 자산 — 재작성 시 계승할 것

1. **Metric(값·상태·출처) 3층 모델** (`models.py`) — "없는 값"을 NO_DATA /
   NOT_APPLICABLE / 판단불가로 구분하는 설계는 금융 도구로서 드물게 정직하다.
2. **"판단불가 ≠ 불합격" 원칙** — 단, 분모 제외가 점수를 올리는 부작용은 고칠 것
   (예: 판단불가 개수를 점수와 나란히 1급 정보로 표시).
3. **네트워크 단일 파일 격리 + 순수 함수 파서** — 오프라인 테스트 가능 구조.
4. **대체 지표를 근거란에 명시하고 README에 한계를 정직하게 쓰는 문화.**
5. 오프라인 테스트 124개의 습관 자체 (다만 문구 결합·픽스처 다양성 문제는 §6 참조).

## 8. 재구축 제안

### 8-1. 데이터 소스 선택지

| 소스 | 주는 것 | 리스크/비용 |
|---|---|---|
| **pykrx** (KRX 스크래핑 라이브러리) | **전 종목** 일별 OHLCV·시가총액·거래대금, 지수, 투자자별 매매동향(기관·외국인·개인), 공매도. **RS 백분위의 필요조건 충족** | KRX 웹 비공식 스크래핑 — 형식 변경 리스크는 네이버와 동급. 단 커뮤니티가 크고 유지보수 활발 |
| **KRX 정보데이터시스템 / Open API** | 상장주식수, 업종 분류, 관리종목·거래정지 목록 | Open API는 신청 필요. 일부는 CSV 다운로드 자동화 |
| **OpenDART** (금감원 공식 API) | **공시 원문**(계약 금액, 상대방, 기간), 사업보고서 재무제표 **5개년+**, 최대주주 지분, 자사주 | 무료 API 키 발급 필요. 공식 API라 **가장 안정적**. 분당 요청 제한 있음 |
| **FinanceDataReader** | 전 종목 리스트, 가격, 지수 | pykrx와 겹침. 보조용 |
| **FnGuide** (comp.fnguide.com) | **컨센서스**(분기·연간), 정리된 재무, 연결/별도 구분 | 비공식 스크래핑. 컨센서스는 여기 아니면 네이버뿐 |
| **네이버 금융** (현행) | 실시간성 시세, 뉴스, 컨센서스 보조 | 지금까지의 모든 문제. **보조 소스로 강등** 권장 |

권장 조합: **가격·수급 = pykrx, 재무·공시 = OpenDART, 컨센서스 = FnGuide(또는 네이버 유지), 메타데이터 = KRX**.
핵심 원칙: 어떤 소스든 **원문 응답을 저장소에 기록하는 계약 테스트**를 두고,
스키마 검증 실패는 조용한 퇴화가 아니라 **시끄러운 실패**로 처리한다.

### 8-2. 권장 아키텍처

```
[일 1회 배치 수집]                [로컬 저장소]           [분석/화면]
pykrx 전 종목 일봉  ──┐
OpenDART 재무·공시  ──┼──▶  parquet 또는 DuckDB  ──▶  전 종목 랭킹 (RS·EPS 백분위)
FnGuide 컨센서스    ──┘      (원본 + 정규화 2층)        ──▶  스크리너 (조건 통과 종목 목록)
                                                        ──▶  종목 상세 (현재 앱의 후신)
```

- 수집과 조회를 분리한다. 조회는 로컬만 읽으므로 즉답이고, 전 종목 연산이 가능해진다.
- 원본 응답(raw)과 정규화 테이블을 분리 저장 — 파서 버그 수정 시 재수집 없이 재처리.
- 데이터 신선도(수집 시각, 재무 기준 분기, 컨센서스 기준일)를 1급 컬럼으로.

### 8-3. 단계별 로드맵

| 단계 | 내용 | 이것으로 가능해지는 것 |
|---|---|---|
| **1. 유니버스 파이프라인** | pykrx 전 종목 일봉 수집 → parquet/DuckDB 적재 → 일 1회 갱신. 우선주·스팩·ETF·관리종목 필터 | **RS Rating 백분위 (진짜 L)**. 전 종목 스크리닝의 토대 |
| **2. CANSLIM 재판정** | OpenDART 5개년 재무로 C(EPS+매출+가속)·A(3년 연속) 원전 구현. S에 가격 방향 조건, I에 기관 순매수, M에 분산일 카운트 | 원전 정의에 충실한 7개 게이트. 스크리너 화면 |
| **3. 베이스·매매 규칙** | 베이스 패턴 인식(컵위드핸들·플랫), 피벗 산출, 피벗 +5% 매수 구간, -7~8% 손절·익절 규칙 표시 | N의 실질 구현. "선별기"에서 "투자 도구"로 |
| **4. 백테스트 하네스** | 모든 임계값을 파라미터화, 과거 데이터로 승률·손익비 검증 | 한국 시장용 임계값 튜닝. 임의 상수 퇴출 |
| **5. 재료 분류 고도화** | 키워드 → 부정어 사전 + 근접 규칙, 또는 LLM 분류 + OpenDART 계약 금액 필터 | N의 재료 판정 신뢰성. (또는 N에서 재료 AND 조건 자체를 제거하는 선택지도 검토) |

1~2단계만으로도 현재 도구가 하는 일을 원전 기준으로 대체하고 남는다.
3단계부터는 범위 확장이므로 1~2단계 후 다시 결정해도 된다.
